# FAILURES.md

A live log of what broke and how it got fixed. Written at the moment of breakage, not reconstructed afterwards.

The Buildathon form asks *"what broke, and how you got out"* and says it is the first thing they read. This file is the raw material for that answer.

Entries below are in strict chronological order (2026-08-30 through 2026-08-31) and unedited after the fact — including the wrong first guesses, the reverted fixes, and the one entry (gpt-5-nano vs. gpt-5-mini) left open with no fix applied at the time it was written, resolved only in the entry that follows it. If it reads rough, that's the log doing its job.

## Format

```
### <date> — <one-line symptom>
**Broke:** what actually happened, concretely
**Cause:** the real cause, not the first guess
**Fix:** what changed
**Kept:** what this changed about the design, if anything
```

Rules for keeping this useful:

- Write the entry **before** fixing, while the symptom is still confusing. The confusion is the interesting part.
- Record wrong first guesses. "I assumed X, it was actually Y" is the most valuable line in any entry.
- Include the near-misses — things that nearly shipped broken and got caught by a test or a sanity check.
- Do not clean it up later. Rough is credible.
- If `Kept:` is non-empty, that failure changed the architecture. Those are the entries worth talking about in the video.

## Log

### 2026-08-30 — generated CSVs had CRLF (and doubled CRs) on Windows
**Broke:** while building the money-handling round-trip tests for `generate.py`, a quick manual check of a naively-written CSV showed `b'a,b\r\r\n1,2\r\r\n'` — a doubled `\r` before every `\n`, not just a normal CRLF.
**Cause:** two independent things stacked. First, Python's default text-mode file writing on Windows translates every `\n` byte to `os.linesep` (`\r\n`) on write. Second, the stdlib `csv.writer` *also* defaults its own line terminator to `\r\n` regardless of platform. Writing `\r\n` through a text-mode handle that then translates `\n`→`\r\n` produces `\r\r\n`. I assumed "no newline handling in my code" meant "no newline surprises" — wrong; the default is never neutral on Windows.
**Fix:** open every generated file (CSV and JSON) with `newline=""` to disable the platform translation, and pass `lineterminator="\n"` explicitly to `csv.writer`. Verified byte-for-byte: `b'a,b\n1,2\n'`.
**Kept:** DATA_SPEC.md's "byte-identical on any machine" requirement is not automatically true just because the generator has no explicit newline logic — it has to be enforced at every `open()` call. Added a determinism test that inspects raw bytes for `\r` rather than trusting a round-trip-through-pandas comparison, since that would have hidden this exact bug (pandas would decode-and-recompare consistently within one OS and never notice the encoding was platform-dependent).

### 2026-08-30 — git itself would have re-broken the same newline fix on checkout
**Broke:** nothing shipped broken, but a `git show :data/order_ledger.csv | xxd` check while staging commit 10's fixtures confirmed the risk: `git config core.autocrlf` is `true` here (both locally and globally). That setting converts LF to CRLF on checkout for anything git guesses is text.
**Cause:** the staged blob was correctly LF-only (autocrlf only rewrites on the way *out*, and the working file was already LF), so nothing looked wrong in the diff or the warnings — `git add` printed "LF will be replaced by CRLF the next time Git touches it," which is easy to read as noise. It is not noise: it means a future `git clone` or `git checkout -- data/order_ledger.csv` on a machine with autocrlf on would silently hand back a CRLF file, while a fresh `unbatch generate --seed 42` run would still produce LF — the exact byte-identical guarantee this session already fixed once, reopened one layer up.
**Fix:** added `.gitattributes` forcing `text eol=lf` on `data/**` and `cache/**`, so git normalizes to LF on checkout regardless of the client's `core.autocrlf`.
**Kept:** a newline-determinism fix at the application layer isn't sufficient for files that are also committed as "evidence" — the version-control layer needs its own explicit line-ending policy, not an inherited platform default. Same lesson as the first entry, one layer up.

### 2026-08-30 — rebalancing to smaller batches made credits go negative
**Broke:** commit 12's rescale (18 batches of 4-9 lines down to 68 batches of 2-4 lines, to hit ~70 credits over ~200 payments) immediately hit `pydantic_core.ValidationError: credit_paise must be non-negative` while building the bank statement baseline — twice, from two different causes, back to back.
**Cause:** first guess was that only the settlement_split batches were at risk (splitting a batch's lines in half can put a refund-heavy half on its own). Fixing that wasn't enough — the very next run failed on `CHARGEBACK_BATCH_INDEX` instead: the flat `CHARGEBACK_FEE_PAISE` (Rs 500) penalty plus normal fees can exceed a 2-line batch's other line entirely, since the old 4-9-line batches had enough unrelated lines to absorb a fixed penalty that a 2-line batch can't. Smaller batches don't just scale down proportionally — a fixed cost that was noise against 8 lines is structural risk against 2.
**Fix:** two changes. (1) Organic (non-forced) refund/partial-refund rolls now check projected batch headroom before committing — `MIN_BATCH_NET_BUFFER_PAISE` — and silently revert the order to `captured` if a refund would push the running total negative, rather than trusting probability. (2) `CHARGEBACK_BATCH_INDEX` (and settlement_split, ambiguous_composition) are forced to a fixed 4 lines via `_FORCED_N_LINES` instead of the general 2-4 range, so there's always enough headroom for their fixed costs.
**Kept:** any batch that carries a fixed-cost break (a flat fee, a full refund) needs either a headroom check or a forced minimum size — "at least one of every break type" and "smaller batches" are in real tension, not just a scale change. Added `_SPECIAL_BATCH_INDICES` to suppress organic noise on every hand-built batch, so the two don't fight each other.

### 2026-08-30 — rounding_delta's guaranteed gap silently became zero
**Broke:** after fixing the negative-credit errors above, `generate()` ran clean, but a manual check of the rounding_delta credit showed `delta=0` — the one break type whose entire point is a nonzero paise-level gap had none.
**Cause:** the original 4-9-line batches had enough lines that *some* line's fee almost always landed on a rounding boundary by chance. At 2-4 lines, that's no longer reliable — this specific seed's `LARGE_VALUE_BATCH_INDEX` batch happened not to hit one. The "floor" case of L3's tolerance band had been relying on an unstated probabilistic assumption the whole time; shrinking the batch size just made it visible.
**Fix:** force two CARD-method lines in that batch to an exact gross (`ROUNDING_BOUNDARY_GROSS_PAISE = 500_025`) that lands on a half-paise fee boundary individually (500025 × 2% = 10000.5 → 10001 each) but sums to a whole-paise batch total (1000050 × 2% = 20001.0 exactly) — a deterministic 1-paise gap, not a hoped-for one.
**Kept:** every "at least one" guarantee in this generator now has to be true by construction, never by the odds looking favorable at a given batch size — this is the second time in one session a "probably enough lines" assumption broke silently (see chargeback, above).

### 2026-08-30 — three break types didn't actually test anything once L0 existed
**Broke:** the first integration test for L0 (against the real seed-42 fixtures + ground_truth.json) flagged 3 "false matches": `refund_in_window`, `chargeback_deduction`, and `ambiguous_composition` all resolved cleanly at L0 — the stage that's only supposed to catch `clean` and (accidentally, via UTR presence) whatever else ties out exactly.
**Cause:** two separate design gaps in the milestone-1/2 generator, invisible until a real matching stage existed to expose them. (1) `refund_in_window`/`chargeback_deduction`: the bank credit is `sum(all lines in the UTR group)`, and `compute_expected_batches` (the "rules" side L0/L1 compare against) grouped the *same* lines the *same* way — so the refund/chargeback was already netted into both sides identically, and there was never a delta for any stage to reconcile. Worse, I'd also let *organic* refunds/chargebacks land in otherwise-`clean` batches during the commit-12 rebalance, which would have hit the identical bug the moment one of those got unlucky. (2) `ambiguous_composition`: the target credit was a whole, single-UTR batch — exactly the shape L0/L1 are designed to resolve trivially, so the "genuine alternate subset" I built for L2 never got a chance to matter; UTR+exact-amount+exact-date won every time.
**Fix:** (1) `compute_expected_batches` now sums only `PAYMENT`-type lines — the naive pre-refund/chargeback total a merchant would expect — while the actual bank credit still correctly includes the refund/chargeback, per ARCHITECTURE.md's own description of what a real settlement nets out. Also removed organic (non-forced) refund/chargeback/adjustment generation entirely; that content now lives *only* in its own dedicated batch, never mixed into a `clean` one. (2) The `ambiguous_composition` target now uses only all-but-the-last line of its batch as the credit — the last line is a permanent, deliberately unclaimed leftover — so the credit's amount no longer equals its own batch's whole total and L0/L1 correctly decline it, leaving the genuine ambiguity for L2/L4 to actually encounter.
**Kept:** a break type is not "tested" just because ground_truth.json has a label for it — it's tested when a real stage, run against the real data, actually has to work to resolve or correctly decline it. I could not have caught this without building L0 first; this is exactly why the generator and the cascade have to be exercised against each other, not just against the ground-truth schema.

### 2026-08-30 — L2 took 22 seconds and still got ambiguous_composition wrong
**Broke:** the first L2 integration test took 45 seconds to fail, flagging 5 missing/wrong matches. Timing it down: one L2 run over 13 leftover credits took ~22 seconds — compose()'s own tests run in milliseconds, so something was feeding it far bigger candidate pools than the dataset should produce.
**Cause:** `batch.index` (the label every `*_BATCH_INDEX` constant uses to assign a break-type role) was assigned by `enumerate()` over a *sorted-by-date* list of batches. That made index correlate with chronological position — every special-role batch (indices 2-16) landed in the first four calendar days of the window, because that's where sorted ranks 2-16 fall when 103 batches spread over 30 days. Once L0/L1 consumed the `clean` batches' lines, everything left unresolved (all special-role batches) had settled within days of each other, so each one's `[D-3d, D]` window pulled in 36-43 lines instead of the single digits a spread-out dataset would produce — close enough to MAX_POOL=48 to make meet-in-the-middle genuinely slow. I had sorted the dates originally just so bank_statement.csv's baseline felt chronological; I never noticed the index correlation because nothing read `batch.index` as anything but an opaque label until L2 needed date windows to actually mean something.
**Fix:** stopped sorting the date draw — `batch.index` is now uncorrelated with date, so special-role batches land throughout the whole 30-day window (pools dropped to single digits, max 16; full L2 run now takes ~1s). `inject_breaks` already re-sorts the final bank_statement rows by date regardless, so removing the earlier sort changes nothing about the committed output's ordering.
**Kept:** removing the clustering also broke `ambiguous_composition` a second, different way — its decoy batch used to sit at index+1 next to the target purely because adjacent index meant adjacent date; with dates decoupled from index, the decoy could land anywhere in 30 days, and even when it happened to land close, resolving the decoy's own credit at L0 consumed its lines before L2 ever ran, so the "coincidental alternate subset" was gone by the time it could matter. Fixed by moving the decoy pair into `ORPHAN_SETTLEMENT_BATCH_INDEX` instead of a separately-resolving batch — orphan lines are never claimed by any Decision, so they stay in L2's pool for the entire run — and explicitly anchoring the orphan's date to 1-3 days *before* the target (the window only looks backward, so an "after" decoy would never even be a candidate). Two lessons stacked here: an index used purely as a label can smuggle in an unintended correlation the moment something downstream starts caring about a *different* field, and "the decoy resolves independently" is actually incompatible with "the decoy stays available as a competing candidate" once resolution progressively consumes what it matches — an ambiguity that can be resolved away by an earlier stage isn't a real ambiguity.

### 2026-08-30 — L3's tolerance search returned ~90 matches for one credit
**Broke:** this is the best failure in the project so far, because it isn't a bug in the usual sense — the code did exactly what it was written to do, and what it was written to do was wrong. L3 was built as `compose_within_tolerance`: the same meet-in-the-middle machinery as L2's exact composition, but accepting any subset whose sum landed within the tolerance band instead of hitting the target exactly. Run against the real fee_tier_change credit (an 11-line candidate pool after L0/L1/L2 had already claimed everything else), it returned roughly ninety within-tolerance subsets — not one, not two, dozens, spanning every plausible combination of 3-8 lines from that pool. The true composition was in there. So were ~89 coincidences.
**Cause:** I designed L3 by analogy — "L2 but with slack" — without re-deriving what that slack actually does to the search space. Composing exactly is a strong filter: for a random pool, almost no subset sums to precisely the target, so `compose()`'s results are usually the single real answer. Composing within a *band* is a categorically different operation: once any subset landing within ±0.6% of the target counts, the filter stops being "sums to X" and becomes "sums to approximately X", and an 11-line pool has 2^11 = 2048 subsets to draw near-misses from. A band wide enough to cover a genuine fee-tier drift (tens of paise to low thousands, scaled to the credit) is nowhere near tight enough to exclude the combinatorial noise of thousands of unrelated partial sums. My first instinct on seeing ~90 matches was "the band is too wide, narrow it" — wrong instinct: narrowing the band from 0.6% to, say, 0.1% would still leave hundreds of subsets in play at this pool size, and 0.1% would also be tight enough to reject a real half-point fee change, defeating the entire point of having a tolerance stage. There is no band that fixes this, because the problem is the search, not its width.
**Fix:** L3 no longer searches. It checks. `compute_expected_batches` has already grouped settlement lines into real, meaningful aggregates (one net per settlement UTR) — L3 compares the credit directly against each date-windowed batch's already-computed net, `|credit - batch.net|`, and matches only if exactly one batch lands within tolerance. A pool of a dozen lines has thousands of subsets; the same window typically has one or two *batches*. Batches are a real, priced quantity a system has already computed for other reasons — comparing against them has nothing left to be coincidentally right about, because there's no assembly step left to produce a coincidence. `compose_within_tolerance` is deleted from compose.py entirely, along with its dedicated tests; `compose.py` is exact-only now, and rightly so — tolerance was never a composition concern.
**Kept:** "L2 but with slack" is not a valid design derivation for a new stage — every stage's actual search space has to be re-examined on its own terms, not inherited from its neighbour in the cascade table. The instinct to tune a threshold when a result looks wrong is worth resisting on principle, not just on this specific number: a wrong *operation* can look like a mistuned parameter right up until you check whether any parameter value would actually fix it.

### 2026-08-30 — running the cascade twice doubled every count
**Broke:** immediately after wiring `unbatch run --no-llm` end to end, I ran it a second time to eyeball the output again — same seed, same data, no changes in between. `unbatch exceptions` came back with every credit_id listed twice.
**Cause:** `run_id` is derived deterministically from seed + input hash (commit 14), which is exactly what makes two runs of the same data comparable — but I never wrote the other half of that idea. `audit.record` only ever inserts; nothing removed a run's previous rows before writing its new ones. Two runs of the same run_id don't overwrite or merge, they just both land in the table, so every count anything queries — `unbatch exceptions`, and every metric metrics.py will compute next milestone — silently doubles on a second run. Trivial to hit by accident: re-running to check output, restarting after a crash mid-run, or CI re-executing the same seed would all trigger it.
**Fix:** added `audit.clear_run(conn, run_id)`, called at the start of `unbatch run` before the cascade writes anything. Deletes any existing rows for that run_id first, so a re-run replaces rather than accumulates.
**Kept:** "the run_id is deterministic" and "the audit log is append-only" are individually correct design choices that combine into a bug if nothing bridges them — reproducibility at the id level doesn't imply reproducibility at the table level unless something enforces it. Added a regression test (`test_rerunning_the_same_run_id_does_not_duplicate_rows`) that runs the same insert-decisions sequence twice and asserts the count stays flat, so this can't silently come back.

### 2026-08-31 — CLAUDE.md's own spec named an API parameter the model rejects
**Broke:** nothing at runtime — caught before the first live call. Building the adjudicator, the up-to-date Claude API reference flagged that `claude-sonnet-5` (and the whole 4.6+/5 model family) rejects `temperature`/`top_p`/`top_k` outright with a 400. CLAUDE.md's own stack line says "Anthropic SDK, `claude-sonnet-5`, temperature 0, JSON out validated by pydantic" — a literal instruction that, followed as written, would have made every L4 call fail on the very first real request.
**Cause:** CLAUDE.md was written against an older assumption about this model family's API surface — sampling controls were a normal way to ask for deterministic output when the file's stack section was drafted, and that surface changed under it. The file describes an API shape, not just an intent, so it can go stale exactly the way code does, and this project's own instruction says its contents "OVERRIDE any default behaviour" — the kind of line that's easy to follow literally into a wall.
**Fix:** `adjudicator._call_model` sends no sampling parameters at all. Determinism for the metrics that matter comes from the prompt-hash cache instead — `--cached` always replays the exact committed bytes, regardless of what a live call would produce on any given day — not from `temperature=0`, which is no longer an available knob on this model.
**Kept:** a spec file naming a specific API parameter is a claim that can expire, same as a memory naming a specific function or flag. Worth a written note when it's caught, not a silent deviation — this entry is that note.

### 2026-08-31 — scaling ambiguous_composition to 7 instances resurfaced two old bugs and one new one
**Broke:** raising `ambiguous_composition` from 1 instance to 7 (D0a — rules-only was resolving 103/105 credits, leaving the adjudicator exactly one genuinely ambiguous case to prove itself on) was meant to be a pure scale-up of an already-working mechanism. The very first regenerate-and-test cycle instead false-matched a completely different credit: `test_l1_resolves_every_narration_mangled_credit_and_nothing_else` failed with L1 resolving an `ambiguous_composition` credit against the wrong batch entirely.
**Cause:** the original single-decoy design forced its decoy batch to 4 lines specifically so `_apply_ambiguous_decoy`'s 2 manipulated lines wouldn't be the *only* lines in the batch — with 2 extra untouched lines, `compute_expected_batches`'s PAYMENT-only `net_paise` for the whole decoy batch (anchor + manipulated + 2 more) never happened to equal the manipulated pair's own sum. I "simplified" each of the 7 new decoys to exactly the 2 lines `_apply_ambiguous_decoy` actually touches, since nothing else looked used — missing that those 2 extra lines weren't padding, they were load-bearing: with exactly 2 lines, both PAYMENT type, the decoy's *whole-batch* net_paise **is** the manipulated pair's sum, which **is** the ambiguous target's amount, so L1 resolved the real target credit against the decoy's own ExpectedBatch as a false "exact" match. My first fix — forcing decoys back to 4 lines — cleared that failure, but the very next full-suite run surfaced a second, different false match: a different `ambiguous_composition` credit resolved at L3 against yet another decoy's *whole-batch total*, which coincidentally fell inside that credit's tolerance band. Same root cause, different threshold: any decoy whose whole-batch total isn't clearly separated from every other credit's amount is a latent collision, and this was always true even in the original 1-instance version — just improbable at n=1, no longer improbable at n=7 decoys competing amid 105 credits.
**Fix (first attempt, then reverted):** padded each decoy with 4 more forced-large lines to push its whole-batch total into a value range (~Rs 1,20,000–1,95,000) clear of both the ordinary batch ceiling (~Rs 1,00,000) and the deliberately-huge LARGE_VALUE/rounding_delta batch (~Rs 4,65,000). This worked — zero false matches — but the full suite's runtime jumped from ~4s to ~47s, and a quick pool-size check showed one credit's L2 candidate pool at 43 lines, a hair under `MAX_POOL` (48). Seven decoys × 4 padding lines is 28 extra settlement lines clustering near 7 anchor dates, which is exactly the batch-clustering failure mode from this file's 2026-08-30 L2 entry, reintroduced one layer up.
**Fix (actual):** neither more lines nor bigger lines — the manipulated line's *type*. `_apply_ambiguous_decoy` now sets the adjusted line's type to `ADJUSTMENT`, not `PAYMENT`. L2's composition search doesn't filter by line type, so the coincidence is exactly as discoverable to L2 as before; but `compute_expected_batches`'s `net_paise` sums PAYMENT lines only, so the decoy's own ExpectedBatch net is now just the small anchor line — nowhere near the target sum, and nowhere near any other credit's amount either. Decoys are back to 2 lines, pool sizes are back to a max of 27, and the full suite is back to ~4s.
**Kept:** the same lesson as 2026-08-30's L2 entry, but one level deeper this time — fixing a coincidence by adding more of the same kind of thing (more lines, then bigger lines) treats the symptom and moves the collision surface around rather than removing it; the actual fix was finding the one field controlling whether a line counts toward the aggregate at all. Also: a "padding" line that visibly changes the test suite's wall-clock time is a signal worth stopping for, not routing around — it was the reason I looked at pool sizes at all instead of just accepting the passing test run.

### 2026-08-31 — a response with no text block would have skipped the retry path entirely
**Broke:** the first test for the no-text-block edge case (the model hitting `max_tokens` before emitting any text, so `response.content` has no `text`-type block) failed with an uncaught `_MalformedResponseError` propagating straight out of `adjudicate()`, instead of triggering the documented retry-then-degrade.
**Cause:** I'd put the "no text block" check inside `_call_model`, one layer below where `adjudicate()`'s retry `try/except` actually wraps — that `except` only sat around `_parse_response`, so an exception raised earlier, while fetching the response, had nowhere to land. First guess was that the retry logic itself was wrong; it wasn't — the failure mode was simply being raised outside the block that was supposed to catch it.
**Fix:** moved the check into a small `_require_text()` helper, called from inside the same `try/except` as `_parse_response`, so a missing text block and a malformed JSON body now go through the identical retry-then-degrade path, with token cost from the failed attempt still counted before either failure mode is evaluated.
**Kept:** "never crashes on model output" has to cover every way a response can fail to yield usable text, not only the ways that parse as invalid JSON — the retry/degrade boundary belongs around the whole "get usable text back" step, not just the JSON-parsing half of it.

### 2026-08-31 — the model list I remembered was two generations stale, and the pricing assumption after that was still wrong
**Broke:** nothing shipped wrong — caught before writing a line of adjudicator.py. D0.5 needed a small, cheap OpenAI model, and my first instinct (from training data) was to reach for something in the `gpt-4.1`/`gpt-4o-mini` family. Fetching OpenAI's actual pricing page instead showed a completely different current lineup: a `gpt-5.6` family (Sol/Terra/Luna) launched July 2026, sitting *above* an already-existing `gpt-5`/`gpt-5-mini`/`gpt-5-nano` tier in the same table. My mental model of "the current models" was current as of training, not as of now — two naming generations behind, not just one version bump.
**Cause:** treating "the model I remember" as "the model that exists" is exactly the failure mode CLAUDE.md's own instruction to check docs first was written to prevent, and it would have been silent — a `gpt-4o-mini` call would not have errored, it would have just used a model OpenAI still runs but has since undercut on price and superseded on the pricing page's own ordering. The second near-miss was assuming the *newest-looking* name is the cheapest: `gpt-5.6-luna` reads like the budget option in its own family ("optimized for cost-sensitive workloads") and is 4x the price of the older `gpt-5-nano` ($0.20/$1.20 vs $0.05/$0.40). Newest generation and cheapest tier are independent axes; picking on brand-recency instead of the actual number in the table would have quietly overspent the whole session's budget four-fold.
**Fix:** fetched the raw pricing table directly from developers.openai.com and sorted by number, not by name recency. `gpt-5-nano` ($0.05/$0.40 per 1M tokens) is the actual cheapest model OpenAI lists, full stop — confirmed it isn't a retired/legacy tier by cross-checking an independent news source on the `gpt-5.6` launch date rather than trusting either source alone.
**Kept:** "check current docs, don't assume from memory" has to mean the *whole* lineup, not just confirming the one model name already in mind still resolves — an unfamiliar family launching mid-training-cutoff-to-now is invisible to memory by construction, and a table sorted by naming scheme hides the actual cost ordering underneath it just as easily as no table at all.

### 2026-08-31 — gpt-5-nano scored 25% break-reason accuracy; gpt-5-mini scored 0%, not better
**Broke:** nothing in the pipeline — both models returned clean, schema-valid JSON on all 12 L4 credits, zero malformed responses, zero retries, on both runs. The break is in the numbers: `gpt-5-nano` classified 3 of 12 credits correctly (25% break-reason accuracy) against the real seed-42 dataset's 12 L4 credits (7 `ambiguous_composition`, 4 `tolerance_ambiguous`, 1 `unrelated_credit`), missing every single `ambiguous_composition` case (called them `tolerance_ambiguous`, `unrelated_credit`, or `date_skew` instead). Stepping up to `gpt-5-mini` — same prompt, same `reasoning_effort="minimal"`, only the model changed — scored **0 of 12**, strictly worse: every `tolerance_ambiguous` credit was called `rounding_delta` instead (recognizing "small delta" but missing the ambiguity — two competing candidate batches — entirely), and the one `unrelated_credit` (genuinely nothing to tie to, ground truth `resolvable: false`) was confidently matched under `refund_in_window` instead of declined.
**Cause not yet fully isolated:** the mini run also produced `count_match_rate: 1.0` and `exception_rate: 0.0` on this run — every credit "resolved," including the one that is deliberately unresolvable. METRICS.md's own words: *"A 100% match rate means something is wrong."* Two candidate causes, not yet distinguished: (1) gpt-5-mini's confidence calibration on this task may simply be poor — it reported confidence 0.72-0.88 on cases it got completely wrong, high enough to clear the 0.60 human_review floor and, on 3 of 12, the 0.85 auto-accept ceiling; (2) `l4_llm.py`'s own prompt may be steering this — `build_prompt`'s wording describes the batch handed to the model as "already selected by the rules layer," which was true when an earlier stage made a confident pick, but for these 12 credits it is actually L4's own naive nearest-by-amount-and-date guess (`_pick_batch_and_candidates`), offered *because* the rules layer explicitly could not decide. Telling the model the batch was already selected, for exactly the credits where that is false, may be biasing it toward confirming rather than interrogating the pick.
**Fix:** none applied yet — reported both numbers to the user rather than picking a model or rewriting the prompt unilaterally, since neither "step up again" nor "fix the prompt wording" was in scope for this checkpoint.
**Kept (so far):** "cost is not the binding constraint, accuracy is" survived contact with real data in the way that matters — a bigger/pricier tier was not automatically a better one on this task, and the honest result is a regression, not an improvement. Whether the fix is a bigger model, a corrected prompt, or a change to what counts as a "resolved" credit when `human_review_required` is true is an open question, not yet decided.

### 2026-08-31 — the real bug was the candidates, not the model: whole batches can't equal a strict subset
**Broke:** picked apart the previous entry's open question by pulling the actual prompts sent for the three misclassified `ambiguous_composition` credits. One example, `txn_qE40fAraVNqTIA`: the "expected batch" the prompt called "already selected by the rules layer" had a delta of -139,488 paise (nearly Rs 1,400) against the credit — nowhere near a real match. Ground truth's actual answer (`pay_uVg8G9mcy1htc0`, `pay_tYSPH8UCiY5DCQ`, `pay_oPe5JEKCIYk7eg` — 3 lines) *was* present in the prompt, but only as one of four alternate candidates, and even there it was offered as all 4 lines of its batch, not the true 3 — meaning even a model that picked it exactly would still register as a false match against ground truth's multiset comparison.
**Cause:** `l4_llm.py`'s candidate logic (built in Part C, before this milestone's `ambiguous_composition` scale-up) only ever compares whole `ExpectedBatch` objects — every line sharing a settlement UTR — against the credit's amount. `ambiguous_composition`'s ground truth is deliberately a *strict subset* of one batch (the generator always leaves one line permanently unclaimed, specifically so a whole-batch exact tie can never happen — see the 2026-08-30 entry on this exact mechanism). No candidate offered to the model could ever equal the correct answer exactly, for any model, at any size. Stepping from nano to mini couldn't have fixed this — the right answer was never representable in what either model was shown.
**Fix:** `l4_llm.py` now re-runs `compose.compose()` itself — the same bounded exact-sum search L2 already does — over the credit's own date-windowed `candidate_lines`, before falling back to the whole-batch heuristic. A credit reaching L4 in the with-LLM arm only ever has 0 or >=2 exact-sum subsets this way (L2 already claimed anything with exactly 1); >=2 is *provable*, rules-established ambiguity, so the outcome is forced to `exception` regardless of the model's reported confidence — no arbitrary pick is ever committed as a match. Needed `cli.py`'s candidate-line rebuild (previously L2-only) extended to also run before L4.
**Near-miss caught mid-fix:** the first version ran this same search unconditionally, including under `--llm-only`. The full test suite hung — `test_cli_run_llm_only.py`'s stubbed 105-credit run never returned inside a 60-second hard-killed rerun. Two problems in the same line: running `compose()` against a *completely unpruned* pool (nothing resolved yet, since `--llm-only` skips L0-L3 entirely) for every one of 105 credits is a real performance cliff, not just a slow test — and conceptually, quietly re-deriving L2's composition search inside `--llm-only` would smuggle a rules capability into the one arm whose entire point is having none, undermining the ablation's own comparison. Fixed by gating the search on `ctx.llm_only == False`; `--llm-only` keeps the original (structurally limited) whole-batch heuristic on purpose — scoring worse there is expected, not a bug to route around.
**Kept:** a stubbed test with an empty `candidate_lines` list is not a stand-in for "this code path works" — every existing test in `test_l4_llm.py` kept passing through this entire investigation because none of them ever populated `candidate_lines`, so the new search path silently no-opped in every one of them. The bug was only ever going to be visible against real, adversarially-constructed data — which is exactly why "run it for real before trusting the stub suite" was worth the two live-model measurements it cost to surface this.
**Resolution:** re-ran both models against the fixed candidates. `gpt-5-nano` jumped from 25% to **83% break-reason accuracy** (10/12, including 7/7 `ambiguous_composition` correct) with **zero false matches** — count_match_rate landed at exactly the rules-only baseline (93/105), meaning nano correctly deferred to exception on every one of the 12 hard credits rather than guess, and simply named *why* far better than before. `gpt-5-mini` was never re-run once nano's fixed-candidate number came in an order of magnitude better at 1/6 the per-call cost — the model swap from the previous entry is reverted; `adjudicator.MODEL` is back to `gpt-5-nano`. The lesson from the earlier entry held exactly as stated: the fix was the candidates, not the model, and no model was ever going to out-classify a broken input.

### 2026-08-31 — D4's keyless-reproduction check found arm C's JSON wasn't byte-identical
**Broke:** running D4's actual verification (unset `OPENAI_API_KEY`, `--cached` all three arms, diff against the key-present baseline) — the exact check CLAUDE.md invariant 6 asks for, run for real rather than assumed — arms A and B diffed clean, byte for byte. Arm C's `metrics` JSON did not: `exception_break_type_counts` had the same keys and the same counts, just in a different order, between two runs of the identical `--cached` command.
**Cause:** `exception_break_type_counts` is built by iterating `exception_ids`, which is a plain `set[str]`. CPython's set iteration order for strings depends on hash randomization (`PYTHONHASHSEED`), which is re-randomized per process by default — so two separate `uv run` invocations of the *same* deterministic data can still serialize this one field's keys in a different order, even though every underlying number is identical. Arms A and B happened not to show it only because their `exception_ids` sets are smaller (2 and 12 entries) and this run's hash seeds didn't happen to reorder them — not because they were actually immune to the same bug.
**Fix:** `metrics.py` now iterates `sorted(exception_ids)` instead of the raw set. Verified by running `unbatch metrics` twice in separate processes and diffing — identical both times, including after the fix was applied to a case (arm C, 12 distinct break types) that had already shown the flake.
**Kept:** "the numbers are the same" and "the file is byte-identical" are different claims, and CLAUDE.md invariant 6 is written as the second, stricter one on purpose — a set's iteration order is exactly the kind of hidden nondeterminism that only shows up on some field, on some run, and passes every test that doesn't literally diff two independent invocations. This is the second time this project has hit "looked deterministic, wasn't, only visible on the real verification" (see the 2026-08-30 CRLF entries) — the fix pattern is the same both times: don't trust output shape, diff actual bytes from two independent runs.

### 2026-08-31 — `unbatch bench --seeds` crashed on exit despite every seed scoring correctly
**Broke:** first real run of the new `bench --seeds 42,43,44,45,46,47` command exited non-zero with a `PermissionError: [WinError 32] The process cannot access the file because it is being used by another process`, raised out of `TemporaryDirectory.__exit__`'s cleanup — after all six seeds had already generated their fixtures and scored cleanly. `bench_multiseed.json` was never written, since that write sits after the `with tempfile.TemporaryDirectory()` block, and the exception fired during that block's own `__exit__`, before control ever reached it.
**Cause:** `_score_rules_only_for_seed` opens a sqlite3 connection per seed via `audit.connect()` and never closes it. On Linux/macOS an unlinked-but-open file is still deletable; on Windows an open handle to a file inside the temp directory blocks `shutil.rmtree` from removing it at all, not just that one file. Every other place in this codebase that opens a connection (`run`, `metrics`, `exceptions`) lives for the lifetime of the whole CLI process, which exits and releases the handle anyway — this is the first code path where a connection needed to be closed *before* something else (temp-dir cleanup) could proceed within the same process.
**Fix:** `_score_rules_only_for_seed` closes its connection before returning the scored report.
**Kept:** a helper that opens a resource scoped to "one seed's worth of work" inside a loop that reuses the same temp directory across iterations needs to close that resource itself — it can no longer rely on process exit to do it, the way every prior caller of `audit.connect` implicitly could.

### 2026-08-31 — multi-seed variance surfaced two distinct false-match paths, both invisible at seed 42
**Broke:** the whole point of `bench --seeds` — every number in README.md/test_end_to_end.py comes from seed 42 alone, whose rules-only false-match rate is a true, exactly-reproduced 0.0%. Run across six seeds instead of one, false-match rate is nonzero on four of them: 43 → 1.08%, 44 → 1.06%, 45 → 1.08%, 46 → 2.11% (only 42 and 47 land at 0.0%). Precision drops as low as 97.89% (seed 46) against the 100% every existing test and the README both quote.
**Cause — two separate mechanisms, not one:**
1. **L3 tolerance false-accepts `ambiguous_composition` credits** (seeds 44, 45, 46 — all 4 false matches, `reason=tolerance_band_match`). `ambiguous_composition`'s ground truth is deliberately a strict subset of its batch: the generator always leaves exactly one line permanently unclaimed, specifically so no *exact* match (L0/L1/L2) can ever equal it. L3 (rewritten per the 2026-08-30 entry) compares a credit directly against whole date-windowed batch nets, `|credit − batch.net| ≤ tolerance` — correct for `fee_tier_change`/`rounding_delta`, whose gap is real fee drift, bounded by construction, within the tolerance band. But `ambiguous_composition`'s gap is just "the value of whichever line got left out" — nothing bounds that below `max(50 paise, 0.6% × credit)`. On seeds where the unclaimed line happens to be small, L3 confidently resolves the credit against its own whole batch — the exact false accept L4's 2026-08-31 exact-composition-candidate fix exists to prevent, except L3 runs first and has no equivalent guard.
2. **L2 exact-composition coincidental collision** (seed 43, `reason=single_composition_match`, a 9-line subset accepted at confidence 0.9 against a `fee_tier_change` credit that has nothing to do with those 9 lines). `fee_tier_change` is deliberately *not* an exact match against any real batch — that's what routes it to L3 in the first place. But L2's candidate pool (up to 48 unrelated lines from other batches in the date window) is large enough that some unrelated subset can, by pure chance, sum to exactly the same paise amount. L2 sees a genuinely unique exact-sum subset — correct from its own local view — and accepts it. ARCHITECTURE.md's own L3 section calls composing exactly "a strong filter... almost no subset of a random pool sums to precisely a target." True on average; "almost no" surfaced once in six seeds.
**Fix:** none applied. Both are gaps in already-deliberate, already-documented stage designs (L3's whole-batch tolerance compare, L2's uniqueness-implies-correct accept rule), not local implementation slips — closing either means giving a stage judgment it doesn't currently have (L3 would need to know a credit is `ambiguous_composition`-shaped without reading ground truth; L2's accept rule would need a secondary sanity bound beyond uniqueness, e.g. on subset size or line spread). This session's rules reserve unrequested fixes for genuine local bugs, fixed the same day they're found (see the connection-leak entry immediately above) — a change to L2 or L3's matching logic is a cascade-behaviour change, and this session was told to stop and report rather than make that call unilaterally.
**Kept:** seed 42 being the only seed anyone had run was hiding two distinct false-match paths behind one true, honestly-reported 0.0%. Neither is "the code doesn't do what it was designed to do" — both are the designed behaviour producing the wrong answer on an input distribution wider than one seed. That is the entire argument for `bench --seeds`: one seed's false-match rate is a real fact about that seed and a materially incomplete claim about the system. Flagged to the user rather than fixed; candidate follow-ups if this is picked up later: (a) a cheap ambiguity guard in L3 — escalate instead of accepting when excluding any single candidate line would also land the remainder in tolerance; (b) a size- or date-spread sanity bound in L2 on top of uniqueness before accepting an exact match at 0.9 confidence.

### 2026-08-31 — the real bottleneck at scale wasn't the composition search, it was the audit log
**Broke:** first `bench --scale 500` run reported L0 — UTR string matching, `O(credits × batches)` but otherwise trivial — taking 0.84s of a 1.2s total, dwarfing L2 (0.15s) despite L2 being the stage ARCHITECTURE.md calls "the algorithmic centrepiece" and the one this benchmark was built expecting to find degrading. A hand-run of `l0_utr.run()` alone, no audit writes, on the identical data took 0.014s — sixty times faster than the same stage inside the real cascade.
**Cause:** `audit.record()` calls `conn.commit()` after every single row (see audit.py) — a synchronous disk-flush per decision. At production scale (105 credits) that's invisible. At 500 credits, L0 alone resolves 464 of them, i.e. 464 individual fsync-equivalent commits, measured directly at 0.88s for the write loop against 0.014s for the matching itself — the audit log, not the matching algorithm, is what shows up in the timing. Confirmed by isolating the two: `l0_utr.run()` timed alone vs. the same decisions piped through a loop of `audit.record()` calls.
**Then, separately:** `bench --scale 1000` didn't finish — it hung past 120s. Instrumenting stage-by-stage showed L0 and L1 completing in under 2s (matching the commit-cost finding above, scaled up), then L2 never returning. Pulling the actual date-windowed pool sizes for the 82 credits that reached L2 found six credits sitting at *exactly* 48 lines (`MAX_POOL`) and another ten in the low-to-mid 40s — the range where `compose.py`'s meet-in-the-middle genuinely does 2^24-ish enumeration per half, which its own docstring already documents as "several seconds in pure Python." `PoolTooLargeError` only refuses pools *over* 48; it does nothing to protect against a pool that lands *at* 48. `DEFAULT_TIMEOUT_S=5.0` bounds any *one* credit, but nothing bounds the total when a dozen-plus credits each cost several seconds back to back — the per-credit guard is not a per-run guard.
**Fix:** none applied — both are true costs of already-deliberate designs (commit-per-decision durability, a hard pool cap with no discount for a pool that's merely close to it), not implementation slips, and changing either is exactly the kind of behaviour change this session was told to stop and report on rather than make unilaterally. `bench --scale` does not raise `MAX_POOL`/`MAX_SUBSET` to make the number look better — see bench_scale.json for what actually happened at scale 5000, run to completion once this was understood.
**Kept:** ARCHITECTURE.md predicted correctly that L2 would degrade at scale, but for a different reason than stated — the failure mode isn't "the pool cap starts firing" (a fast, cheap refusal), it's "pools cluster just *under* the cap," where the bounded search is legal but expensive, and there is currently no bound on how many of those a single run can hit. Separately, and not predicted by ARCHITECTURE.md at all: the audit log's per-row commit is the actual dominant cost of the two lower stages, which never even touch composition. Two independent scale bottlenecks, discovered by two independent measurements, neither one where the design doc said to look.

### 2026-08-31 — a headline metric was a property of one dataset, and the fix for it targeted the wrong mechanism
**Broke:** implemented the L3 guard the previous entry's diagnosis called for — refuse a within-tolerance match when the delta exactly equals a real settlement line's net, so a whole missing line can't be mistaken for fee/rounding drift — and verified it with targeted unit tests (an available line exactly matching the delta now correctly falls through; ordinary drift with no matching line still resolves; the real seed-42 `rounding_delta`/`fee_tier_change` cases still resolve at L3 with the pool populated for real, not vacuously — `test_l3_tolerance_integration.py`'s own cascade helper had never rebuilt `candidate_lines` before L3 either, so it needed the same fix to actually exercise the new code path). Re-ran `bench --seeds 42,43,44,45,46,47` expecting the false-match rate to drop on seeds 44/45/46. It did not move at all: 43 → 1.08%, 44 → 1.06%, 45 → 1.08%, 46 → 2.11%, byte-identical to the pre-fix `bench_multiseed.json` in every field except the two cost-per-unit numbers E8 added afterward.
**Cause:** the previous entry's diagnosis — "the deliberately-unclaimed line happens to be small enough that the credit lands within tolerance of its own whole batch" — was written from a plausible mechanism, not from checking which batch each false match actually landed on. Pulling the real decisions for all four false matches (seeds 44 and 45's one each, 46's two) and looking up which `ExpectedBatch` each one's `matched_payment_ids` actually belongs to showed every single one resolved against a *different, unrelated* batch — seed 44's case, for instance, has a genuinely missing line worth 880,466 paise (nowhere near its ~18,231-paise tolerance band), but a completely separate batch on the same date happens to have a net only 17,817 paise from the credit, which is within band. This is not "a whole line mistaken for noise" — it is the same "two unrelated quantities coincidentally land within a narrow target of each other" shape as the L2 exact-sum collision already documented and explicitly left alone, just occurring at the tolerance-comparison step instead of the composition-search step. The guard just implemented is a correct, verified fix for a real false-accept shape that simply isn't the one present in this six-seed sample.
**Fix:** the guard stays — it closes a genuine gap (see l3_tolerance.py's docstring) even though it happens not to fire on the currently observed data, and there is no principled reason to revert a correct hardening because a different bug turned out to be the one actually measured. The cross-batch tolerance coincidence itself is not fixed, per this session's explicit instruction: no widening or narrowing `TOLERANCE_RATE`/`TOLERANCE_FLOOR_PAISE`, and no new mechanism invented to distinguish a coincidental collision from a real one without information the system doesn't have (the same call already made for L2's collision). `bench_multiseed.json` is recommitted with the identical rates, now reflecting a run made after the fix rather than before it.
**Kept:** this is exactly the finding the multi-seed work exists to produce, one layer deeper than expected — not just "the 0.0% false-match rate is a property of seed 42," but "the fix aimed at the one measured seed's failure was aimed at a plausible-sounding cause that turned out to be wrong, and only checking the actual matched batch on real data caught it." A hypothesis about *why* a metric moves needs the same verification-against-real-data discipline as the metric itself — "the delta is small enough to be noise" and "the delta happens to equal a coincidentally nearby batch" produce the identical symptom (a within-tolerance false accept) and are indistinguishable without actually tracing which batch got matched. The measured floor after this fix: false-match rate is 0.0% on 2 of 6 seeds (42, 47) and 1.06–2.11% on the other 4, entirely attributable to coincidental collisions at L2 and L3 rather than a remaining logic gap — reported as a floor, not fudged to zero.

### 2026-09-01 — three genuine construction bugs in the adversarial generator, caught only by running the real cascade against it
**Broke:** the first cascade run against the newly-built `generate_adversarial` output was wrong in three separate ways, none of them visible from reading the generator code in isolation. (1) The near-cap-pool credit's two true lines shared one settlement UTR — `compute_expected_batches` grouped them into a single aggregate batch whose net equalled the credit exactly, so L1 resolved it on an amount+date exact match before L2's composition search ever ran at all, defeating the entire point of the scenario.
