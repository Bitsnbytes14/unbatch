# DATA_SPEC.md

Synthetic, seeded, generated by `generate.py`. Shaped like real Razorpay settlement data — domain realism is free marks.

**Scale:** 150 settlement-relevant records across ~18 settlement batches over a 30-day window. The brief asks for 50+; clearing it 3× costs nothing since it's generated.

**All money is `int` paise.** The CSVs carry rupee decimal strings; parsing to paise happens once, at load.

## order_ledger.csv

The merchant's own record of what was sold.

| field | type | notes |
|---|---|---|
| `order_id` | str | `order_<14 alnum>` |
| `payment_id` | str | `pay_<14 alnum>` |
| `amount` | decimal str | gross, rupees |
| `currency` | str | `INR` |
| `status` | enum | `captured` \| `refunded` \| `partially_refunded` \| `failed` |
| `captured_at` | ISO 8601 | Asia/Kolkata |
| `customer_ref` | str | |
| `method` | enum | `upi` \| `card` \| `netbanking` \| `wallet` |

## settlement_report.csv

The gateway's line-level breakdown.

| field | type | notes |
|---|---|---|
| `settlement_id` | str | `setl_<14 alnum>` |
| `settlement_utr` | str | the UTR that should appear in bank narration |
| `payment_id` | str | FK to ledger |
| `type` | enum | `payment` \| `refund` \| `chargeback` \| `adjustment` |
| `gross` | decimal str | |
| `fee` | decimal str | rate varies by `method` |
| `tax` | decimal str | GST on fee |
| `net` | decimal str | `gross - fee - tax`, negative for refund/chargeback |
| `settled_at` | ISO 8601 | T+1 or T+2 from capture |

## bank_statement.csv

What the bank actually shows. The noisiest source, as in reality.

| field | type | notes |
|---|---|---|
| `txn_id` | str | bank's own ref |
| `value_date` | ISO date | |
| `narration` | str | free text, often truncated or mangled |
| `credit` | decimal str | blank for debits |
| `debit` | decimal str | blank for credits |
| `balance` | decimal str | running |

Narration templates vary realistically: `NEFT-<UTR>-RAZORPAY SOFTWARE PVT`, `IMPS/<UTR>/RZPY`, truncated `NEFT-AXISP000123...`, and occasionally no UTR at all.

```json
      "payment_ids": ["pay_...", "pay_..."],
      "break_type": "fee_tier_change",
      "resolvable": true

```

**Read only by `metrics.py`.** Never imported under `stages/`.

## Injected break types

The generator deliberately produces each of these. This catalogue is the spine of the whole project — it defines what the cascade must handle, what the model is asked to classify, and what the exception list should contain.

| break type | what it looks like | should resolve at |
|---|---|---|
| `clean` | UTR present, amount exact | L0 |
| `narration_mangled` | UTR truncated or absent, amount exact | L1 |
| `settlement_split` | one batch paid as two credits on consecutive days | L2 |
| `refund_in_window` | a refund nets out inside the batch, so credit < expected | L2 / L4 |
| `chargeback_deduction` | chargeback + chargeback fee deducted | L2 / L4 |
| `fee_tier_change` | fee rate changed mid-window, small delta | L3 |
| `rounding_delta` | paise-level rounding on GST | L3 |
| `date_skew` | T+2 instead of T+1, lands outside naive window | L2 |
| `duplicate_utr` | same UTR reused across two settlements | L4 |
| `unrelated_credit` | inbound transfer that is not a settlement at all | exception |
| `orphan_settlement` | settlement report line with no bank credit | exception |
| `ambiguous_composition` | two different payment subsets compose the same amount | L4 |

The last three are **meant to stay unresolved or need judgment**. A run that reports 100% resolution is a broken run — it means something is matching things it shouldn't. The honest exception list is the deliverable, not an embarrassment.

## Generator requirements

- Fully seeded. `--seed 42` must produce byte-identical CSVs on any machine.
- Emits a break-type distribution summary to stdout so the mix is visible without opening the files.
- Money math is done in paise internally, formatted to 2dp on write.
- At least one instance of every break type above, with the long tail weighted realistically (most records clean).
- One deliberately large-value credit among the breaks — so the value-weighted metric differs from the count metric and the distinction is visible in the report.
