# DATA_SPEC.md

This file specifies the shape of the three input files the pipeline reads, and the break types the generator deliberately injects into them. Read it if you need to know what a field means, what a break type looks like, or why the dataset is sized the way it is.

The data is synthetic and seeded, generated by `generate.py`. It is shaped like real Razorpay settlement data, since domain realism is free marks.

**Scale:** 105 bank credits, composed from ~300 payment-level settlement lines (plus refund, chargeback, and adjustment lines) over a 30-day window. The brief asks for 50+; this clears it more than 2× over, at no cost since it's generated.

**All money is `int` paise** (1/100 of a rupee, India's smallest currency unit). The CSVs carry rupee decimal strings; parsing to paise happens once, at load.

## order_ledger.csv

The merchant's own record of what was sold.

| field | type | notes |
|---|---|---|
| `order_id` | str | `order_<14 alnum>` |
| `payment_id` | str | `pay_<14 alnum>` |
| `amount` | decimal str | gross, rupees |
| `currency` | str | `INR` |
| `status` | enum | `captured` \| `refunded` \| `partially_refunded` \| `failed` |
| `captured_at` | ISO 8601 | Asia/Kolkata |
| `customer_ref` | str | |
| `method` | enum | `upi` \| `card` \| `netbanking` \| `wallet` |

## settlement_report.csv

The gateway's line-level breakdown.

| field | type | notes |
|---|---|---|
| `settlement_id` | str | `setl_<14 alnum>` |
| `settlement_utr` | str | the UTR (Unique Transaction Reference, the bank's own reference number for a transfer) that should appear in bank narration |
| `payment_id` | str | FK to ledger |
| `type` | enum | `payment` \| `refund` \| `chargeback` \| `adjustment` |
| `gross` | decimal str | |
| `fee` | decimal str | rate varies by `method` |
| `tax` | decimal str | GST (Goods and Services Tax, India's VAT) on fee |
| `net` | decimal str | `gross - fee - tax`, negative for refund/chargeback |
| `settled_at` | ISO 8601 | T+1 or T+2 from capture, i.e. one or two business days later |

## bank_statement.csv

What the bank actually shows. The noisiest source, as in reality.

| field | type | notes |
|---|---|---|
| `txn_id` | str | bank's own ref |
| `value_date` | ISO date | |
| `narration` | str | free text, often truncated or mangled |
| `credit` | decimal str | blank for debits |
| `debit` | decimal str | blank for credits |
| `balance` | decimal str | running |

Narration templates vary realistically: `NEFT-<UTR>-RAZORPAY SOFTWARE PVT`, `IMPS/<UTR>/RZPY`, truncated `NEFT-AXISP000123...`, and occasionally no UTR at all. `unbatch generate --noise <0.0-1.0>` (project milestone E10) degrades these further on top of this baseline variety: truncation mid-UTR, transposed digits, O/0 and I/1/l substitution, inconsistent separators, bank-style wrapping text, and case inconsistency. `--noise 0.0` (the default) reproduces the templates above exactly.

## ground_truth.json

```json
{
  "credits": [
    {
      "txn_id": "...",
      "settlement_ids": ["..."],
      "payment_ids": ["pay_...", "pay_..."],
      "break_type": "fee_tier_change",
      "resolvable": true
    }
  ]
}
```

`settlement_ids` is a list, not a single id. Most credits tie to a settlement batch of several lines (one per payment), so a credit composed from a real batch needs more than one.

**Read only by `metrics.py`.** Never imported under `stages/`.

## Injected break types

The generator deliberately produces each of these. This catalogue defines what the cascade must handle, what the model is asked to classify, and what the exception list should contain.

| break type | what it looks like | should resolve at |
|---|---|---|
| `clean` | UTR present, amount exact | L0 |
| `narration_mangled` | UTR truncated or absent, amount exact | L1 |
| `settlement_split` | one batch paid as two credits on consecutive days | L2 |
| `refund_in_window` | a refund nets out inside the batch, so credit < expected | L2 / L4 |
| `chargeback_deduction` | chargeback + chargeback fee deducted | L2 / L4 |
| `fee_tier_change` | fee rate changed mid-window, small delta | L3 |
| `rounding_delta` | paise-level rounding on GST | L3 |
| `date_skew` | T+2 instead of T+1, lands outside naive window | L2 |
| `duplicate_utr` | same UTR reused across two settlements | L4 |
| `unrelated_credit` | inbound transfer that is not a settlement at all | exception |
| `orphan_settlement` | settlement report line with no bank credit | exception |
| `ambiguous_composition` | two different payment subsets compose the same amount | L4 |
| `tolerance_ambiguous` | two different settlement batches' nets both fall inside L3's tolerance band of the same credit | L4 |

The last four are **meant to stay unresolved by rules alone, or need judgment**. A run that reports 100% resolution is a broken run: it means something is matching things it shouldn't. The exception list, reported honestly, is a deliverable, not an embarrassment.

`ambiguous_composition` (7 instances) and `tolerance_ambiguous` (4 instances, added in milestone D0a; see FAILURES.md's 2026-08-31 entries) are deliberately the largest non-clean categories, not one-offs. With only 1 genuinely ambiguous credit, there was nothing for the LLM adjudicator (the stage that classifies why a break happened; see ARCHITECTURE.md's L4 section) to meaningfully prove itself against. Raising these two pulled directly from the clean pool, so the overall clean rate dropped from about 85% to about 75%. That drop is reported as a direct, honest consequence of the change, not tuned back toward the old number.

## Generator requirements

- Fully seeded. `--seed 42` must produce byte-identical CSVs on any machine.
- Emits a break-type distribution summary to stdout so the mix is visible without opening the files.
- Money math is done in paise internally, formatted to 2dp on write.
- At least one instance of every break type above, with the long tail weighted realistically (most records clean).
- One deliberately large-value credit among the breaks, so the value-weighted metric differs from the count metric and the distinction is visible in the report.
